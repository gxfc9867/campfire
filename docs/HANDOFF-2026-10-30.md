## 1. 用户目标（原话要点）

- **通用化优先**，不是给每个 agent 写适配器。「任何 agent 都能接围炉」。
- 参考 IM 的形态（微信能扫码绑定 → 围炉也应能），但只参考形状，不复用微信协议。
- MCP 是必须做的通用面，**以读取/查询记忆为主**，也包括传递信息。
- 记忆 = 原文 + 摘要 + 向量检索；配置一个 LLM 做「信息整理」，不参与群聊。
- 成员 = agent 上的会话；单聊/群聊都能定位到会话。
- 不做多租户；鉴权用静态密钥；死信要独立页面；时间以服务端为准；数据目录可整体搬迁；部署只承诺 Linux/WSL/Docker（Windows 仅开发）。

### 3.3 jobs 路径

- **agent job 启动即失败**：`~/.codebuddy/logs/job-<id>.log` 里 `Error: listen EADDRINUSE 127.0.0.1:54600`（worker 继承网关端口）

- `respawn` 会消费 pending reply，但同样会踩端口冲突

### 3.4 wbipc 逆向（结论：此路不通）

- 发现文件：`~/.workbuddy/wbipc/endpoint.json` → `{"endpoint":"\\\\.\\pipe\\wbipc-<hash>","ticket":"<base64url>"}`
- 协议：**JSON + `\n`**；握手 `session_hello → session_challenge → session_prove → session_hello_ack`
  - `ticket_id` = `sha256(ticket).hex.slice(0,16)`
  - `proof = HMAC-SHA256(ticket, transcript).base64url`
  - `transcript` = 4 字节大端长度前缀依次拼接 `[wbipc-s|wbipc-c, "1", endpoint, clientNonce, serverNonce]`
- 结果：**握手成功**（server_proof 校验通过），但可见管道只有 3 个：
  - `wb.entitlement` → `subscription.check`
  - `wb.request` → `http.fetch`
  - `wb.wecom-a2a` → `authorize`
- 换 `client.kind` 无效；猜 12 个会话管道名全部 `E_PIPE_UNKNOWN`
- **结论：wbipc 是能力代理，不是应用控制面；桌面会话没有对外写入口**

## 6. 坑（务必看）

1. **不要跑 `codebuddy -p`**：会写坏共享凭据（`missing-key`），把网关登录态一起带崩。历史教训。
2. **不要在桌面 App 的环境里直接起 codebuddy**：环境里有 `SERVER__PORT=50609`（App 自己的服务端口），子进程会抢端口 → `EADDRINUSE`。必须在干净 shell 里跑（`unset SERVER__PORT`）。
3. **本次事故**：我（如意）在 App 环境里反复起 ACP 子进程，把当前会话搞掉线了。**接手后不要在当前会话进程内直接起 codebuddy**，用独立终端/新 shell。
4. `CODEBUDDY_SERVICE_PROXY_URL` 被删会触发 `setProxy TypeError`（非致命，但会刷屏）。
5. 写任何真实会话文件前**先备份**；验证后比对 `cmp`，确认没改。
6. 会话 `cwd` 不存在时 agent 行为异常（refusal/报错），填对路径。
7. 网关口令：`CODEBUDDY_GATEWAY_PASSWORD` env 可固定；否则每次随机打印。`~/.codebuddy/settings.json` 的 `gateway.password` 已删（恢复随机）。
8. 不要动 `dsh-bridge` 生产容器与 NAS 上的数据。
9. `sidecar.config.json` 必须放仓库根（不是 `sidecar/`）。
10. 围炉投递只认 `@提及`；不带 @ 不产生任务。
