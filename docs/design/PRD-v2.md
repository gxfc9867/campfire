## 二、背景与目标

### 2.1 一句话定义

**围炉是一个自托管的多成员 AI 群聊中枢**：多个 agent 以「成员」身份坐在同一个群里，各有名字、头像、人设与会话；平时休眠，被 @ 或被消息触发时醒来干活，产物回到群里。

### 2.2 要解决的问题

同时使用多个 AI 工具时，它们互相看不见，也看不见主人在忙什么。想要「一个群，坐着几个各有分工的助手」，会撞上三堵墙：

| # | 痛点 | 具体表现 | 现有产品的缺口 |
|---|---|---|---|
| P-1 | 接不进来 | 每个 AI 工具接入方式不同，逐个写适配器是无底洞 | IM 的 bot 生态按平台定制，跨 agent 无标准 |
| P-2 | 一直醒着太贵 | 为随时回话，每个 agent 都得常驻 | 常驻进程的内存/额度成本由用户承担 |
| P-3 | 没有连续性 | 每次唤起都是新进程，不记得昨天说过什么 | 上下文窗口有限，跨工具无共享记忆 |

### 2.3 第二代问题（本轮的真正起点）

初代跑通后暴露：**「接进来」不等于「用起来」**。

| # | 问题 | 现象 | 影响 |
|---|---|---|---|
| G-1 | 分身是假的 | 围炉里的 agent 只是「回话的接口」，本体软件里没有真实会话；切回本体看不到围炉发生了什么 | 用户不信任，认为在跟「假人」说话 |
| G-2 | @ 被当成记忆边界 | 只有被 @ 的成员收到消息，其余完全不知道群里发生过什么 | 群不是共享空间，协作断裂 |
| G-3 | 接入仍定制化 | DSH、WorkBuddy、第三方一家一套接法 | 无法形成生态，每个新 agent 都是新项目 |
| G-4 | 记忆无处安放 | 群消息越来越长，agent 上下文装不下 | 只能靠人复述，回溯成本高 |

### 2.4 产品定位

**是**：自托管的群聊内核 + 记忆主机 + 通用接入标准。
**不是**：IM 替代品、多租户 SaaS、模型供应商、agent 运行时。

### 2.5 成功指标

> 目标值为**建议基线**，需卿哥确认后锁定。口径见 §10.4。未确认前不得作为对外承诺。

| # | 指标 | 口径 | 建议目标 | 测量方式 | 现状 |
|---|---|---|---|---|---|
| M-1 | 第三方接入耗时 | 从拿到文档到跑通一致性测试的净工时 | ≤ 2 小时（n≥3 次取中位数） | 接入者计时 + 访谈 | 未测 |
| M-2 | 投递成功率 | 在线成员 5 分钟窗口内成功投递数 ÷ 应投递数 | ≥ 99.5% | 服务端埋点 | 未测 |
| M-3 | 首次响应时延 | 消息落库 → 成员首条回复落库，取 P95 | ≤ 30s（大模型直连）／≤ 90s（桥/插件） | 服务端埋点 | 未测 |
| M-4 | 记忆检索命中 | 20 题人工评测集，top-5 含正确答案的比例 | ≥ 70% | 人工评测 | 未测 |
| M-5 | 摘要覆盖率 | 已生成摘要的消息数 ÷ 应覆盖消息数 | ≥ 95% | 服务端统计 | 未测 |
| M-6 | 连续运行稳定性 | 7 天内非计划重启次数、消息丢失条数 | 0 次 / 0 条 | 运行日志 + seq 连续性校验 | 未测 |
| M-7 | 资源占用 | 空载常驻内存；2C2G 单机可承载 | ≤ 150MB；10 群 × 20 成员可用 | 压测 | 未测 |

**指标缺口说明**：v1.0 全文无任何可衡量目标，只有「功能跑通」。本版补入 M-1–M-7，并在验收章（§13.4）规定测量时点。

## 三、名词与术语

| 术语 | 定义 | 易混淆点 |
|---|---|---|
| **Owner（主人）** | 围炉的唯一管理员，持主人口令登录 Web | 不是「群主」，没有多用户体系 |
| **Member（成员）** | 群里的参与者，可是人、agent、系统 | 成员 ≠ 渠道；一个成员可绑多个渠道 |
| **Channel（渠道）** | 外部接入方在围炉的注册身份，持渠道令牌与 scopes | 渠道令牌泄露 = 可以该成员身份发言 |
| **Binding（绑定）** | `成员 × 群 → 外部会话引用` 的映射 | 绑定失效不等于成员被删 |
| **External Session（外部会话）** | agent 软件侧的会话实体（DSH session / WorkBuddy task） | WorkBuddy 的「任务」就是会话 |
| **Anchor Session（锚点会话）** | 用户手建、用于承接围炉消息的普通会话 | 不能是 automation 生成的一次性会话 |
| **Update（更新）** | 可投递事件（消息新建/编辑/删除、成员变动、投递丢弃），带 `updateId` | 不是消息本身；一条消息可产生多条 update |
| **Cursor（游标）** | 成员在某个群上的读取位置（按 `seq`，不按时间） | 游标过期需走摘要补读 |
| **Wakeup（唤醒级别）** | `reply` 必须回 / `notify` 只注入不回 / `none` 只入库 | 不是「能不能看见」，是「要不要开口」 |
| **Coalesce（合并窗口）** | 窗口内多条消息合并为一次投递，默认 `{30s, 20 条}` | 不是节流；`reply` 不因合并丢失 |
| **Presence（在线态）** | `reachable`（能接指令）+ `ready`（能立刻干活）两维 | 不要合并成一个「在线」 |
| **Digest（成员记忆）** | 成员自己维护的一段摘要，用户可改，白盒可见 | 与「群摘要」不是一回事 |
| **Summary（群摘要）** | 由外接生成式模型对群消息做的滚动摘要 | 不是向量；向量只能编码不能生成 |
| **Embedding（向量）** | 消息的语义向量，用于 top-k 检索 | 需单独配置 embedding 模型 |
| **Conformance（一致性测试）** | 24 条黑盒用例，任何实现可跑 | 通过 ≠ 功能完整，只证明契约兼容 |
| **ACP** | WorkBuddy 的 HTTP Agent Client Protocol，用于把消息写进真实会话 | 平台私有协议，非公开标准 |
| **Driver（驱动）** | 成员被唤醒的方式：`llm` / `pull` / `cli` / `webhook` | 驱动可换，人设与记忆不随之改变 |

### 4.2 本期不做

| 不做项 | 原因 | 归类 |
|---|---|---|
| 多租户 / 多用户注册 | 单家主产品；数据结构预留 `ownerId` | 后续版本（无排期） |
| OAuth 2.1 / 动态授权 | 第一版静态密钥；MCP 客户端支持度不明 | 后续版本 |
| 自动拉起 agent 会话 | 平台侧 `session/new` 不可用、worker 端口冲突未解 | 后续版本（解 Q18 后） |
| 服务端提示词拼装 | 职责边界：围炉管消息，agent 管思考 | **永久不做** |
| 复用微信/企微协议 | 封闭渠道只能参考形状 | **永久不做** |
| Webhook 主动推送（默认开启） | 出站为主；webhook 可选且默认关闭 | 本期不做（能力保留） |
| 多实例水平扩展 | SQLite 单机定位 | 后续版本 |
| 富文本协同编辑 / 音视频通话 | 超出群聊内核范围 | **永久不做** |

> 规则：**「后续版本」与「永久不做」必须分开写**。v1.0 把两者混在 §3.3，导致 P2 又出现「自动拉起会话」，自相矛盾。

## 五、方案对比与选型

> v1.0 缺失本章，直接给结论。评审时无法回答「为什么不用现成 IM」。本章补齐。

### 5.1 产品形态

| 方案 | 做法 | 接入通用性 | 记忆可控 | 部署成本 | 实时性 | 开发成本 | 结论 |
|---|---|---|---|---|---|---|---|
| **A. 自建群聊内核**（当前） | 自己做消息、成员、投递、记忆 | 高（一套契约） | 完全自有 | 中（需一台常开机器） | 高（长轮询/SSE） | 高 | **推荐** |
| B. 寄生现有 IM | Slack / Telegram / Discord + 各家 bot + 外部记忆库 | 低（每家 bot 一套） | 受平台限制 | 低 | 高 | 低 | 备选：≤3 人小团队更划算 |
| C. 纯 MCP，不做群聊 | 把消息存在 MCP server，靠客户端定时拉 | 中（仅 MCP 客户端） | 自有 | 低 | **低**（MCP 无法主动唤醒） | 低 | 不满足「被 @ 就叫醒」 |
| D. 只做协议层 | 只发布 Channel API 规范，不做 UI | 高 | 无 | 无 | — | 低 | 无法交付完整体验 |

**推荐 A 的理由**：
1. 需求 G-1（本体留痕）要求写进 agent 自己的会话，平台侧 API 不可控，寄生方案无法保证；
2. 需求 G-4（记忆主机）要求原文+摘要+向量都在自己手里，平台方不提供；
3. 需求 G-3（通用化）要求一套契约接所有 agent，IM 的 bot 生态是反例。

**不选 B 的原因**：Slack/TG 的 bot 只能拿到平台投递的消息，无法控制「未 @ 也注入上下文」的语义，也无法保证会话留痕；且数据出境/合规不可控。
**不选 C 的原因**：MCP 是请求-响应模型，服务端无法主动唤醒 agent，直接违背「被 @ 就叫醒」。
**不选 D 的原因**：没有 UI 就没有「群」的产品形态，用户无法验收。

### 5.2 接入驱动模型

| 方案 | 机制 | 常驻成本 | 通用性 | 会话留痕 | 结论 |
|---|---|---|---|---|---|
| 内置适配器 | 为每个 agent 写代码 | 无 | **低**（封闭软件适配成本高） | 取决于实现 | 已否决（用户明确否掉） |
| CLI 唤醒 | 桥拉起 CLI 进程 | 低（跑完即退） | 中（需可非交互调用） | 差（每次新进程） | 仅作兜底 |
| **长轮询 pull** | 成员常驻拉流 | 中（sidecar 常驻，agent 可休眠） | **高**（任何语言） | 中 | **推荐为主路** |
| **原生插件** | 用 agent 自己的渠道机制 | 低 | 低（一家一插件） | **好**（会话原生可见） | **推荐为增强** |
| MCP | 工具调用 | 无 | 高 | 无 | 只做读写面，不做唤醒 |

**结论**：主路 = Channel API 长轮询；增强 = 原生插件（DSH）；特例 = HTTP-ACP 桥（WorkBuddy）；兜底 = CLI/适配器。**四条路并存，但对外只承诺一条标准面。**

### 5.3 会话绑定模型

| 方案 | 语义 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| **1:1（`chatId="*"`）** | 一个成员一个会话，跨群共用 | 记性最好，配置最简 | A 群内容会出现在 B 群回复里 | **默认** |
| 1:N（每群一个） | 每 `群×成员` 独立会话 | 群间彻底隔离 | 记性分散，配置复杂 | 进阶可选 |
| 无绑定 | 不指定会话 | 无 | 无留痕，违背 G-1 | 不做 |

**必须向用户明示**：默认模式下跨群共享上下文，接入页与成员卡片都要有一句话说明，不能只在文档里写。

### 5.4 记忆架构

| 方案 | 能力 | 成本 | 结论 |
|---|---|---|---|
| 仅原文 | 精确回溯 | 存储 | 不足（上下文装不下） |
| 原文 + 摘要 | 快速了解「发生了什么」 | 生成式调用 | 可接受的最小集 |
| **原文 + 摘要 + 向量** | 精确定位「那件具体的事」 | 摘要 + embedding | **推荐** |
| 摘要 + 向量，不存原文 | 省存储 | 丢失可追溯性 | 不做（审计与导出需要原文） |

**选型结论**：三档并存；摘要用生成式模型（向量模型不能生成文字）；整理服务是后台进程，**不是群成员、不参与对话**；未配置模型时诚实降级为 `implemented:false`，不返回假数据。

### 5.5 演进路径

| 阶段 | 内容 | 触发条件 |
|---|---|---|
| 本期（v2.0 基线） | 补齐前端欠账 + 真机验收 + 文档同步 | 立即 |
| 下一版 | 一键连接（配置分发 + 授权页）、Bot API 兼容层 | 本期验收通过 + ≥3 个第三方接入诉求 |
| 远期 | 自动拉起会话、多租户 | Q18 解决 / 出现第二家主 |

## 六、用户角色与使用场景

### 6.1 角色

| 角色 | 是谁 | 核心诉求 | 优先级 | 验证状态 |
|---|---|---|---|---|
| **P0 主人（卿哥）** | 同时用多个 AI 工具、有自建能力的重度用户 | 几个 AI 在一个群里协作；每个有真实会话与记忆；@ 谁谁说话 | 第一 | 已确认为真实用户 |
| P1 自托管用户 | 有 NAS/服务器的技术用户 | 数据在自己手里；接自己的 agent；不依赖云 | 第二 | **假设，未验证** |
| P2 agent 开发者 | 想让自己的 agent 接入的人 | 一份契约、一个测试套件，快速接完 | 第三 | **假设，未验证** |

### 6.2 用户故事

| 编号 | 故事 | 优先级 |
|---|---|---|
| US-01 | 作为主人，我想在群里 @ 某个 agent，让它在我熟悉的那个软件里回我，以便确认「它真的在干活」而不是一个假接口 | P0 |
| US-02 | 作为主人，我想让没被 @ 的成员也知道群里发生了什么，以便它们后续接话时不用我复述 | P0 |
| US-03 | 作为主人，我想让 agent 记得三天前定过的方案，以便不用每次重新交代背景 | P0 |
| US-04 | 作为主人，我想在一个群里同时指挥几个 agent 分工，以便把一件事拆开并行 | P0 |
| US-05 | 作为主人，我想和某个 agent 单聊且不外溢到群，以便处理私事 | P1 |
| US-06 | 作为主人，我想在界面上管理成员的接入令牌与连接状态，以便不用敲 curl | P1 |
| US-07 | 作为第三方开发者，我想按一份契约接入自己的 agent，以便不用读源码 | P1 |
| US-08 | 作为主人，我想在换机器时整体搬走数据，以便不丢历史 | P1 |

**验收标准（GWT）**

- **US-01**：Given 成员已绑定会话且在线；When 我在群里 @ 它并发一句话；Then 它的本体软件里该会话新增一轮问答，且群里出现同一条回复。
- **US-02**：Given 群里有 3 个成员；When 我 @ 其中一个；Then 另外两个收到 `notify` 级上下文，且不强制产生回复。
- **US-03**：Given 群里 3 天前讨论过方案 A；When 我问「上次定的哪个方案」；Then agent 通过 MCP 检索到该消息并正确回答。
- **US-05**：Given 我与某成员存在单聊；When 我在单聊里发言；Then 群内不可见，且该内容不进入群摘要与群向量索引。
- **US-06**：Given 我是主人；When 我打开成员详情；Then 能看到渠道令牌列表（脱敏）、最近一次投递时间、连接状态。
- **US-07**：Given 我只有接口文档；When 我实现最小客户端；Then 能跑过 24 条一致性测试，无需读围炉源码。

### 6.3 场景地图

## 九、业务流程与状态流转

### 9.1 主流程：一条 @ 消息的完整链路

```
主人发消息（含 @如意）
  → 服务端落库，生成 seq / updateId
  → 计算 wakeup：被 @ 者 reply，其余成员 notify
  → 合并窗口（30s / 20 条）内聚合
  → 各成员按驱动拉取（长轮询）或推送（插件/桥）
  → agent 在自己会话中生成回复（工具调用在会话侧执行）
  → 回帖：POST /v1/messages（clientMsgId 幂等）
  → 落库、广播、更新未读
  → 推进各成员游标（ack）
```

**分支**：
- B1 成员离线 → 消息入队，恢复后摘要 + 最近 20 条补投；
- B2 队列满 → 丢最旧 `notify`，保留 `reply`，记 `dropped`；
- B3 游标过期 → `cursor_expired` → 补读；
- B4 会话失效 → `binding_invalid` → 提示重填，不静默失败；
- B5 接力深度 ≥ 3 → 阻断并留系统消息。

**异常**：见 §12。

### 9.2 状态机

**（1）消息投递**

| 当前 | 触发 | 下一状态 | 允许操作 |
|---|---|---|---|
| 待投递 | 成员拉取/推送成功 | 投递中 | 取消、重试 |
| 投递中 | 收到回执 | 已回执 | 查看 |
| 投递中 | 超时/失败 | 待投递（重试） | 重试、取消 |
| 待投递 | 队列满被挤出 | 已丢弃 | 查看丢弃原因 |
| 待投递 | 超过保留窗口 | 已过期 | 走摘要补读 |

**（2）成员在线态**

| 状态 | 判定 | 用户可见 | 迁移 |
|---|---|---|---|
| 离线 | 90s 内无拉取/心跳 | 灰点「消息会排队」 | 心跳 → 可唤醒 |
| 可唤醒 | 有拉取但无进行中任务 | 黄点「约 5 秒」 | 接任务 → 就绪；超时 → 离线 |
| 就绪 | 有进行中的处理 | 绿点「正在处理」 | 完成 → 可唤醒 |

**（3）会话绑定**

| 状态 | 判定 | 行为 |
|---|---|---|
| 已绑定 | `externalSessionRef` 有效且探测通过 | 正常投递 |
| 失效 | 探测失败 / 会话被删 | 标 `binding_invalid`，提示重填，不静默 |
| 未绑定 | 新成员未填 | 只入库，不投递；UI 提示 |

**（4）摘要**

| 状态 | 判定 | 行为 |
|---|---|---|
| 未生成 | 无记录或已过期 | 触发时生成 |
| 生成中 | 请求进行中 | 返回旧摘要 + `generating:true` |
| 已生成 | `coversUpToSeq` 有效 | 正常返回 |
| 失败 | 模型报错/超时 | 返回旧摘要 + 错误说明，不返回空 |

### 9.3 并发与顺序规则

1. 同一成员的多条投递**串行**处理，避免会话竞争；
2. 不同成员**并行**，互不阻塞；
3. 回复按落库顺序呈现，不按生成完成顺序；
4. 同一 `clientMsgId` 并发到达时，只允许一条入库，另一条返回同结果；
5. 群解散时正在投递的任务：允许完成，但结果不再广播，记日志。

## 十、数据与埋点

### 10.1 实体关系

```
Owner 1—N Chat
Chat 1—N Message
Chat 1—N Member（通过 chat_members）
Member 1—N Binding（按 chat 维度）
Channel N—1 Member
Chat 1—1 Summary（滚动）
Message 1—1 Embedding（可选）
Message 1—N Job（投递任务）
```

### 10.2 核心数据

| 实体 | 关键字段 | 说明 |
|---|---|---|
| Chat | `id` / `name` / `kind`（group/dm）/ `archivedAt` | 单聊 `id = dm_<handle>` |
| Message | `id` / `chatId` / `seq` / `sender` / `type` / `text` / `replyTo` / `mentions` / `deletedAt` | `seq` 群内单调递增 |
| Member | `handle` / `display` / `avatar` / `driver` / `chats` / `enabled` | 配置存 `members.json`，乐观锁 |
| Channel | `id` / `member` / `name` / `secretHash` / `scopes` / `revokedAt` | 只存哈希，明文仅创建时返回 |
| Binding | `member` / `chatId` / `externalSessionRef` / `wakeupPolicy` / `invalidAt` | `chatId="*"` 为默认 |
| Summary | `chatId` / `summary` / `coversUpToSeq` / `updatedAt` | 超长截断 |
| Embedding | `messageId` / `seq` / `vector` / `model` | 模型变更需重建 |
| Job | `id` / `member` / `chatId` / `status` / `attempts` / `createdAt` | 投递任务 |

### 10.3 埋点事件

| 事件 | 触发时机 | 关键字段 |
|---|---|---|
| `message_sent` | 消息落库 | chatId, senderKind, type, hasMention, replyTo |
| `delivery_attempt` | 每次投递 | member, chatId, updateId, attempt, latencyMs |
| `delivery_acked` | 收到回执 | member, updateId, ackLatencyMs |
| `delivery_dropped` | 队列丢弃 | member, chatId, reason, droppedCount |
| `member_wake` | 成员被唤醒 | member, driver, wakeupLevel, coalescedCount |
| `binding_invalid` | 会话探测失败 | member, chatId, errorCode |
| `summary_generated` | 摘要生成完成 | chatId, coversUpToSeq, tokens, latencyMs |
| `search_executed` | 检索请求 | member, scope, k, hitCount, topScore |
| `cursor_expired` | 游标过期 | member, chatId, cursor |

### 10.4 指标口径

| 指标 | 定义 | 排除项 |
|---|---|---|
| 投递成功率 | 成功回执数 ÷ 应投递数（5 分钟窗口） | 成员主动停用、群已解散 |
| 首次响应时延 | 回复落库时间 − 触发消息落库时间，取 P95 | 人工取消、防环阻断 |
| 检索命中 | top-5 中出现人工标注正确答案的题数 ÷ 总题数 | 未配置 embedding 的群 |
| 摘要覆盖率 | 已覆盖消息数 ÷ 应覆盖消息数（按 `coversUpToSeq`） | 单聊 |
| 消息丢失 | 重启前后 seq 断点数 | 主动删除 |

## 十一、权限与安全

### 11.1 角色 × 功能 × 数据

| 角色 | 功能权限 | 数据范围 | 说明 |
|---|---|---|---|
| Owner（主人） | 全部：建群/解散/成员增删改/令牌管理/死信重试/备份 | 全部群与单聊 | 单账号，无多用户 |
| Channel（渠道） | 读所在群、发消息、读写自己成员记忆、检索所在群 | 仅 token 绑定成员所在群 | scope 最小化 |
| Member（成员） | 无独立登录态，凭渠道令牌行事 | 同上 | 不能冒充其他成员 |
| 匿名 | 仅登录页 | 无 | 除 health 外全部拒绝 |

### 11.2 Scope 清单

`read:chat:<id>` / `write:chat:<id>` / `memory:read` / `memory:write` / `admin`。
默认渠道只给 `read/write` 其所在群 + `memory:read`；`admin` 仅主人会话可用。

### 11.3 凭据管理

| 凭据 | 存储 | 展示 | 轮换 |
|---|---|---|---|
| 主人口令 | 环境变量优先，否则 `data/owner-key.txt`（0600） | 首启打印一次 | 改环境变量重启 |
| 渠道令牌 | 仅 `secretHash` | 创建时明文一次，列表脱敏 | 吊销重建 |
| 成员密钥 | `members.json`（0600） | 创建时一次 | 一键轮换 |
| WorkBuddy Bearer | `~/.campfire/secrets/`（ACL 仅本人） | **永不展示** | 过期重取（28 天） |

### 11.4 合规要求

1. **自托管定位**：数据在用户自己的机器上，围炉不收集、不上传；
2. **凭据自主**：WorkBuddy 通道依赖用户从本机进程读取自己的登录凭据，属用户自主操作，围炉不代为执行、不分发；
3. **风险告知**：接入页首次启用需二次确认；README「高级用法」写清账号安全、协议条款、版本失效三类风险；
4. **数据权利**：用户可整体导出数据目录；可删除单条消息与整群；删除为软删，**物理清理需显式操作**（待实现，见 L-6）；
5. **日志脱敏**：日志不得出现完整 token、手机号、身份证号；示例数据全部虚构；
6. **未成年人**：本产品面向自托管技术用户，不设计面向未成年人的功能与诱导性交互；
7. **强监管提示**：若用于医疗、金融、教育等场景，使用者需自行确认资质与合规要求。
