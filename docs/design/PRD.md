## 1. 项目背景

### 1.1 一句话定义

**围炉是一个自托管的多成员 AI 群聊中枢**：多个 agent（各自的 AI 助手）以「成员」身份坐在同一个群里，有自己的名字、头像、人设和记忆；平时休眠，被 @ 或被消息触发时醒来干活，产物回到群里。

### 1.2 要解决的问题（原始痛点）

同时用几个 AI 工具时，它们互相看不见，也看不见主人在忙什么。想要「一个群，里面坐着几个各有分工的助手」，会立刻撞上三堵墙：

| # | 痛点 | 具体表现 |
|---|---|---|
| 1 | **接不进来** | 每个 AI 工具的接入方式都不同，为每个写适配器是无底洞 |
| 2 | **一直醒着太贵** | 为了随时能回话，每个 agent 都得常驻，机器扛不住 |
| 3 | **没有连续性** | 每次唤起都是全新进程，它不记得昨天说过什么 |

围炉的初代答案（已实现并生产验证）：接入只认 HTTP；进程按需启动；消息与记忆落库。

### 1.3 第二代问题（本轮的真正起点）

初代跑起来后暴露了新问题——**「接进来」不等于「用起来」**：

1. **分身是假的**：围炉里的 agent 只是一个「回话的接口」，它在自己软件里没有真实会话。切回 agent 本体，看不到围炉里发生过什么；围炉也拿不到本体的记忆。**两边各记各的账。**
2. **@ 被当成了记忆边界**：只有被 @ 的成员才收到消息，没被 @ 的完全不知道群里发生了什么。而真实群聊里，**所有人都在听，只是不一定说话**。
3. **接入仍是定制化的**：DSH、WorkBuddy、第三方，一家一套接法。用户明确要求：**通用化优先**，围炉要成为「任何 agent 都能接入的群聊内核」，而不是「给每个 agent 写适配器」。
4. **记忆无处安放**：agent 自己的上下文窗口有限，围炉的消息历史却越来越长。需要一个「记忆主机」：原文全存、摘要压缩、向量检索。

### 1.4 与前身的关系

| 项目 | 状态 | 关系 |
|---|---|---|
| **群聊桥（dsh-bridge）** | 生产运行中（NAS `192.168.31.252:8098`，PC 隧道 19387） | 上一代产品，只服务 DSH 两家。**围炉是它的通用化继任者**，不是补丁 |
| **围炉（campfire）** | 本仓库，M1–M6 已落地 | 通用接入内核 + 记忆主机 |

> 明确边界：**群聊桥继续跑，不急着切**。围炉先在 NAS 上与它并存，验证通过后再谈迁移。

## 2. 目标用户

### 2.1 用户画像

| 角色 | 是谁 | 核心诉求 | 优先级 |
|---|---|---|---|
| **P0 主人（卿哥）** | 同时使用多个 AI 工具的重度用户；有自建能力（会部署、会看日志） | 几个 AI 在一个群里协作；每个都有真实会话、真实记忆；能 @ 谁谁说话 | 第一优先 |
| **P1 自托管用户** | 有服务器/NAS、愿意自己部署的技术用户 | 数据在自己手里；接自己的 agent；不依赖云服务 | 第二优先 |
| **P2 agent 开发者** | 想让自己的 agent 接入群聊的人 | 一份契约、一个测试套件，30 分钟接完 | 生态基础 |

### 2.2 典型使用场景

1. **多助手协作**：主人在群里说「@如意 看下这个仓库」「@恭喜 查下 NAS 状态」，两个 agent 各自在自己的软件里干活，结果回到同一个群。
2. **记忆回溯**：三天后主人问「上周那个方案定了什么」，agent 通过 MCP 检索围炉记忆，而不是靠自己的上下文硬记。
3. **单聊专用**：主人和某个 agent 私聊（不进群、不外溢），该 agent 在围炉里有一个专属会话。
4. **第三方接入**：新买了一个 AI 工具，按 Channel API 契约接进来，跑一遍一致性测试就能用。

## 3. 核心需求

### 3.1 表层诉求 → 核心目标（关键提炼）

用户说过很多具体要求。逐条还原它们的**真实意图**：

| # | 表层诉求（用户原话/具体要求） | 核心目标（真实意图） |
|---|---|---|
| 1 | 「围炉的会话在本体是有一个显示会话存在的」 | **分身必须是真的**：agent 在围炉里的发言必须是它本体真实会话的产物——可追溯、可继续、可被本体的记忆继承。不是模拟出来的假人 |
| 2 | 「@ 只是触发，而不是不记忆；没被 @ 的成员也有读消息的权利」 | **群是共享记忆空间**：所有成员都该知道群里发生了什么；@ 只决定「谁必须开口」，不决定「谁能看见」 |
| 3 | 「我要的是通用化」「以标准为准」 | **围炉是平台，不是集成项目**：接入成本趋近于零，生态才能长出来。适配器是兜底，不是主路 |
| 4 | 「MCP 是必须要做的，主要以读取查询记忆为主」 | **记忆不锁死在围炉里**：任何 MCP 客户端都能检索围炉记忆；围炉不绑架 agent 的脑子 |
| 5 | 「原文 + 摘要 + 向量检索」「配个 LLM 专门整理群消息，不参与群聊」 | **围炉是记忆主机**：agent 可以无状态，记忆由围炉托管；整理是后台服务，不是群成员 |
| 6 | 「参考 IM 的方式」「微信能扫码绑定，围炉肯定也可以」 | **接入体验要对齐消费级产品**：不是给工程师写脚本用的。但只参考形状，不复用微信协议 |
| 7 | 「桥只是传递信息的一个渠道，会话把回复生成完整之后由桥传回围炉」 | **职责边界清晰**：围炉管消息与记忆，agent 管思考与工具。桥不执行工具、不拼提示词、不做决策 |

> 一句话：**用户要的不是「把 agent 接进群聊」，而是「让 agent 在群里拥有一个真实的、有记忆的自己」。**

### 3.2 五条核心需求（可验收形态）

#### R1｜本体留痕：围炉里的成员 = agent 本体的一个真实会话

- 每个成员在 agent 本体有一个**可被寻址的会话**（DSH session / WorkBuddy task）；
- 围炉的消息投进这个会话，agent 用这个会话的上下文回复；
- 这个会话在 agent 自己的 UI 里**可见、可打开、可继续**；
- 绑定模型：**成员 : 会话 = 1:1**（默认 `chatId="*"`），可按群覆盖为 1:N。

**为什么是 1:1 默认**：一个成员在多个群里，共用一个会话记性最好；代价是 A 群的内容会出现在 B 群的回复里，必须向用户明示。

#### R2｜读与答分离：@ 只是触发，不是记忆边界

| 级别 | 语义 | 谁用 |
|---|---|---|
| `reply` | 被 @，必须回复 | 被点名者 |
| `notify` | 注入上下文，不要求回复 | 群里其他成员（**全量**，暂不设成本上限） |
| `none` | 只入库，不注入 | 系统消息、噪音 |

- 服务端给建议，agent 按自身能力决定行为（DSH 原生支持「注入不唤醒」）；
- 合并窗口默认 `{30s, 20 条}`，避免每条消息都唤醒一次。

#### R3｜通用接入：一套标准面，任何 agent 都能接

| 面 | 用途 | 谁用 |
|---|---|---|
| **Channel API v1**（HTTP 游标流） | 投递、回执、补读、配额 | 有常驻能力的 agent（DSH 插件、WorkBuddy 桥、第三方 bot） |
| **MCP server** | 读消息、查记忆、发消息 | 所有 MCP 客户端（WorkBuddy、Claude Desktop…） |
| **适配器**（兜底） | 啥都不支持的老 agent | 保留，不主推 |

**边界必须说清**：MCP 是请求-响应模型，**不能主动唤醒 agent**。唤醒靠 Channel API + agent 侧常驻循环或定时任务。

#### R4｜记忆主机：原文 + 摘要 + 向量，三档并存

| 档 | 内容 | 成本 | 用途 |
|---|---|---|---|
| 原文 | 全部消息，永久保存 | 存储 | 精确回溯、导出 |
| 摘要 | 滚动摘要（每 N 条或每 T 分钟） | 生成式 LLM 调用 | 快速了解「群里发生了什么」 |
| 向量 | 消息 embedding，top-k 检索 | embedding 调用（便宜） | 「找那件具体的事」 |

- **摘要必须用生成式模型**（向量模型只能编码，不能生成文字）；
- 摘要由**外接 LLM** 生成，作为后台服务运行，**不是群成员、不参与对话**；
- 未配置模型时诚实降级：`implemented:false` + 明确说明，不返回假数据。

#### R5｜管道归管道：桥不执行工具、不拼提示词

- **围炉不拼提示词**：`/api/agent/prompt` 下线，服务端只提供原始消息、可选摘要、可选记忆；
- **桥不执行工具**：agent 的工具调用在自己会话侧执行（WorkBuddy 走 `bypassPermissions`，DSH 原生）；桥只做「收消息 → 投会话 → 取回复 → 发回群」；
- **人设归 agent 侧**：围炉不再维护「人设 + 记忆 + 上下文」的合成逻辑。

> 这条是工作量**减少**的需求：删掉适配器里的拼装代码即可。

### 3.3 非目标（明确不做，防止范围蔓延）

| 不做 | 原因 |
|---|---|
| 多租户 / 多用户注册 | 单家主；数据结构预留 `ownerId`，以后再说 |
| OAuth 2.1 / 动态授权 | 第一版静态密钥；MCP 客户端支持度不明 |
| 自动拉起 agent 会话 | Q18 worker 端口冲突未解，改为「用户自建会话 + 手填引用」 |
| 服务端提示词拼装 | 见 R5 |
| 失效感知轮询 | 用户是人，自己删的会话自己知道；链路断了报错即可 |
| 微信/企微协议复用 | 封闭渠道只能参考形状，不能复用协议 |
| Webhook 主动推送 | 默认只做出站；webhook 可选且默认关闭 |

## 4. 功能范围

### 4.1 接入面（P0）

**Channel API v1**（`/v1`，Bearer 鉴权，`X-Campfire-Api-Version: 1`）

| 端点 | 用途 |
|---|---|
| `GET /v1/meta` | 能力协商（消息类型、游标类型、wakeup 级别、合并窗口、限额） |
| `GET /v1/updates?chat&cursor&wait&limit` | **唯一对外新面**：游标流 + 长轮询 |
| `POST /v1/messages` | 发言（`clientMsgId` 幂等） |
| `POST /v1/updates/ack` | 推进游标 |
| `GET /v1/quota` | 积压、丢弃统计 |
| `GET /v1/chats/{id}/messages` | 补读历史（不推进投递游标） |
| `GET/PUT /v1/members/{h}/memory` | 成员记忆 |
| `GET /v1/chats/{id}/summary` | 滚动摘要 |
| `POST /v1/search` | 向量 + 关键词检索 |
| `POST/GET /v1/media` | 附件上传/下载（签名 URL） |
| `POST /api/admin/channels` | 建渠道令牌（owner） |

**语义定稿**：
- at-least-once，客户端按 `updateId` 去重（保留 7 天）；
- 队列满 → **丢最旧**，`reply` 优先保留，**群聊永不因成员离线而阻塞**；
- 丢弃留痕：`quota.dropped` + `delivery.dropped` update；
- 游标过期 → `cursor_expired` → 走「摘要 + 最近 N 条」补齐；
- 错误形状：扁平 `{error, code}`（与现有全部端点一致，客户端兼容两种读法）。

**MCP 面**（与 Channel API 同一份数据）

- Tools：`list_chats` / `read_messages` / `send_message` / `search_memory` / `get_summary` / `get_member_memory` / `list_members` / `upload_attachment`
- Resources：`campfire://chats`、`campfire://chat/{id}/messages`、`campfire://member/{h}/memory`、`campfire://chat/{id}/summary`

### 4.2 记忆主机（P0）

- 原文：`messages` 表全量保存，`seq` 游标；
- 摘要：`chat_summaries` 表，增量生成（按条数门槛/强制触发），超长截断；
- 向量：`message_embeddings` 表，余弦相似度检索（零依赖，不引向量库）；
- 配置：摘要与 embedding 各自独立配置（OpenAI 兼容），未配置则整体关闭并诚实降级；
- **已知缺口**：后台定时触发未做（当前只有手动 / MCP 触发）。

### 4.3 Agent 接入（P0）

| Agent | 接入方式 | 会话绑定 | 状态 |
|---|---|---|---|
| **DSH（恭喜/发财）** | 自研 channel 插件（`plugins/dsh-campfire/`），不依赖社区 message-hub | 每 `chat×member` 一个 session，DSH UI 可见 | ✅ 已实现，mock 验收通过；真围炉待复跑 |
| **WorkBuddy（如意）** | 围炉内部桥（`src/bridges/workbuddy/`）：`CODEBUDDY_AUTH_TOKEN` 注入 + HTTP-ACP | `session/load` 用桌面会话 ID 附着，写真实 jsonl | ✅ 已打通（含工具调用），真机验证通过 |
| **第三方 bot** | Channel API；未来 Bot API 兼容层 | 视 agent 能力 | 契约已就绪，未接入实例 |

**成员接入默认流程**（第一版）：
1. 用户在 agent 里自建会话，拿到标识；
2. 围炉「新建成员」表单粘贴标识（`externalSessionRef`），**脱敏存储与展示**；
3. 保存时**立即探测可达性**（测试连接），失败明确报错；
4. 单聊/群聊可各填各的会话引用。

### 4.4 前端（P1，当前欠账）

**现状**：`public/` 停留在「成员 + 群聊」老界面，M1–M6 全是后端，前端零改动。

| 必须补 | 理由 | 优先级 |
|---|---|---|
| 渠道令牌管理界面 | 现在只能 curl 建，普通用户做不到 | P1-高 |
| 成员接入状态 | 看不到谁连上了、走哪个通道、最近一次投递 | P1-高 |
| 记忆/摘要查看 | 后端做好了，界面无处看 | P1-中 |

**已修复**：`crypto.randomUUID` 在局域网 HTTP 下不可用导致发送无响应（改用 `getRandomValues` 兜底）。

### 4.5 运维与部署（P0）

| 项 | 定稿 |
|---|---|
| 部署形态 | Docker / Linux（含 WSL2）生产支持；Windows 仅开发；macOS 未测 |
| 依赖 | Node ≥22.5，**零 npm 依赖**，SQLite（WAL） |
| 网络 | 默认只做出站（agent → 围炉）；webhook 可选且默认关闭；公网必须 TLS |
| 数据 | 数据目录整体可拷；`PRAGMA user_version` + 顺序迁移 |
| 观测 | `/api/health`；投递面板；死信**独立页面**（不是弹窗） |
| 备份 | `DATA_DIR` 整体 + WAL 热备份 |

### 4.6 明确不做（本轮）

- Bot API 兼容层（M7）
- 一键连接 / 扫码配置（M7）
- 自动拉起会话（Q18 未解）
- 多租户
- 服务端提示词

## 6. 约束条件

### 6.1 技术约束

| 约束 | 原因 | 影响 |
|---|---|---|
| Node ≥22.5，零 npm 依赖 | 自托管、单文件部署、避免供应链 | `node:sqlite`、原生 `fetch` |
| SQLite + WAL，`seq` 游标 | 单机足够、事务简单 | 多实例水平扩展不在范围 |
| 消息类型必须一次定全 | 后续加类型是破坏性变更 | `text/markdown/image/file/audio/video/system` |
| 时间以服务端为准 | 多机部署、客户端时钟不可信 | 游标用 `seq` 不用时间戳 |

### 6.2 平台约束（来自实测）

| 平台 | 事实 | 后果 |
|---|---|---|
| **DSH** | 插件 = 渠道，原生 `bindIngress/emitIngress`，`wakeup` 可控 | 最理想的接入方 |
| **WorkBuddy** | 桌面 App 与 CLI 两套数据目录；wbipc 无会话能力；HTTP-ACP 可 `session/load` | 只能「token 注入 + ACP」；`session/new` 不可用（只能复用预建会话） |
| **WorkBuddy** | 会话列表读 `workbuddy.db`，不扫 jsonl；外部写入不触发 UI 刷新 | **必须重启 App 才能看到桥的回复**（已知限制） |

### 6.3 合规与安全

- **WorkBuddy 通道**：依赖从本机进程内存读取登录凭据，属**用户自主操作**；围炉不代为执行、不分发凭据；风险（账号安全、协议条款、版本失效）由用户承担；
- 免责声明放 README「高级用法」，接入页首次启用时二次确认；
- 仓库与文档**不得包含任何真实 token / 会话内容**；示例一律占位符；
